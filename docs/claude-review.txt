How a Local Ollama Agent Processes a Prompt
When you send a prompt to an Ollama-hosted model, here's what happens end-to-end:

1. HTTP Request
Your client sends a POST request to Ollama's local server (default http://localhost:11434):

/api/generate — raw completion
/api/chat — chat-style with message history
2. Ollama Server (Go process)
The Ollama daemon receives the request and:

Looks up the requested model (e.g., llama3.2, mistral)
Loads the model weights into memory (RAM or VRAM) if not already loaded
Applies the model's chat template — transforms your messages into a single formatted string the model understands (e.g., wrapping with [INST]...[/INST] for Mistral, or <|user|>...<|assistant|> for others)
3. llama.cpp Backend
Ollama delegates inference to llama.cpp under the hood:


Prompt string
    → Tokenizer  →  token IDs  (e.g., "hello" → [15043])
    → Context window check     (truncate if > model's context limit)
    → Forward pass through transformer layers
    → Logits (raw scores for every token in vocabulary)
    → Sampler (temperature, top-p, top-k, repeat penalty)
    → Next token selected
    → Repeat until [EOS] token or max_tokens reached
4. Sampling
Each token is chosen by the sampler, not deterministically:

Temperature — scales logits (0 = greedy/deterministic, 1 = default, >1 = more random)
Top-p (nucleus sampling) — keeps only tokens whose cumulative probability ≥ p
Top-k — limits candidates to the top k tokens
Repeat penalty — discourages repeating recent tokens
5. Hardware Acceleration
llama.cpp offloads layers to:

GPU (CUDA/ROCm/Metal) — fastest; each layer is a matrix multiply on VRAM
CPU — fallback; uses AVX2/AVX-512 SIMD instructions
Hybrid — num_gpu_layers splits layers between GPU and CPU when VRAM is limited
6. Streaming Response
Tokens are sent back as they are generated (streamed by default), so your client receives partial output incrementally rather than waiting for the full response.

7. Context Persistence (for agents)
For agentic use (tool calls, multi-turn):

The full conversation history is re-submitted each turn (stateless per-request)
Ollama caches the KV cache for the prompt prefix, so repeated context doesn't re-process from scratch
Tool call support depends on the model — models like llama3.1 emit structured JSON that the agent framework parses to dispatch tool calls, then re-injects results into the next prompt
Key constraint: everything runs in your local process — no network call leaves the machine. Latency is dominated by model size, quantisation level (Q4 vs Q8), and available VRAM.
